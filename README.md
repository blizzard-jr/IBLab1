# Защищённый REST API

Лабораторная работа №1 по информационной безопасности. Автор: Метель Леонард Валерьевич, P3412.

Java 21, Spring Boot 3.5.16, Maven, PostgreSQL 17. Пользователь регистрируется с логином, паролем и возрастом, входит и получает список профилей по JWT. Пароли и их хэши в API не возвращаются.

## Запуск

Нужны JDK 21, Maven 3.9+, Docker Compose, OpenSSL; Python 3 нужен только для smoke-проверки.
Все команды выполняются из каталога `lab1` (при публикации содержимое этого каталога должно быть корнем репозитория).

```bash
bash scripts/init-env.sh
# Создаёт .env с двумя случайными секретами, существующий файл не меняет.
docker compose up -d --wait
set -a
source .env
set +a
mvn spring-boot:run
```

API: `http://localhost:8080`. PostgreSQL доступен только на `127.0.0.1:55432`; база `secure_api`, пользователь `secure_api`. Пароль БД и ключ JWT читаются из окружения, обязательны и не имеют значения по умолчанию. `.env` исключён из Git. Для другой БД задайте `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`; для другого HTTP-порта — `PORT`.

`JWT_SECRET` — Base64 от минимум 32 случайных байт. Ключ сохраняется в `.env`, поэтому перезапуск приложения не аннулирует действующие JWT. Замена ключа аннулирует все прежние токены. Данные PostgreSQL сохраняются в Docker volume. `docker compose down` останавливает БД без удаления данных; флаг `-v` удаляет данные, поэтому для обычной остановки его не используйте.

## API

| Метод | Путь | Доступ | Результат |
|---|---|---|---|
| POST | `/auth/register` | Публичный | Создание профиля, 201 |
| POST | `/auth/login` | Публичный | JWT, 200 |
| GET | `/api/data?page=0&size=20` | Bearer JWT | Список профилей, 200 |

Регистрация не выдаёт токен автоматически. Логин чувствителен к регистру, уникален и содержит 1–64 символа, не может состоять только из пробелов. Возраст — целое число от 0 до 150. Пароль — 12–72 символа и не более 72 байт UTF-8: это предотвращает усечение bcrypt. При входе используется исходный, не HTML-экранированный логин. Список доступен всем аутентифицированным пользователям согласно ТЗ; размер страницы 1–100, номер страницы 0–100000.

```bash
curl -i http://localhost:8080/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"username":"leonard","password":"Change-me-2026!","age":21}'

curl -i http://localhost:8080/auth/login \
  -H 'Content-Type: application/json' \
  -d '{"username":"leonard","password":"Change-me-2026!"}'

# Подставьте значение token из предыдущего ответа.
curl -i http://localhost:8080/api/data \
  -H "Authorization: Bearer $TOKEN"

# Должен вернуть 401.
curl -i http://localhost:8080/api/data
```

Ответ регистрации: `{"id":1,"username":"leonard","age":21}`.
Ответ входа: `{"token":"...","tokenType":"Bearer","expiresIn":900}`.
Ответ списка: `[{"id":1,"username":"leonard","age":21}]`.

Ошибки: 400 — некорректный JSON/данные; 401 — неверные учётные данные, отсутствующий или недействительный JWT; 409 — занятый логин. Ответы валидации не включают присланный пароль, SQL и стек исключения.

## Меры защиты

### SQL-инъекции

`Users.java` использует `JdbcTemplate` и параметризованные SQL-запросы с `?` для поиска, регистрации и пагинации. Пользовательские значения передаются отдельно от SQL; конкатенации ввода с запросом нет. На уровне PostgreSQL действуют уникальность логина и ограничение возраста. Попытка входа с `' OR '1'='1' --` возвращает 401. Строка с `DROP TABLE` может быть сохранена как логин, но не исполняется как SQL — это проверено тестом.

### XSS

Логины сохраняются в исходном виде. Перед возвратом профиля из регистрации и списка применяется `HtmlUtils.htmlEscape`. `<script>alert(1)</script>` превращается в `&lt;script&gt;alert(1)&lt;/script&gt;`. Числа возвращаются числовыми полями JSON. Spring отдаёт `application/json` и заголовок `X-Content-Type-Options: nosniff`. JWT содержит числовой ID пользователя, а не его ввод. Это HTML-экранирование по ТЗ: клиент также должен использовать безопасный вывод текста и не вставлять данные в JavaScript/HTML через небезопасные DOM-операции.

### Аутентификация

Пароли хэшируются `BCryptPasswordEncoder(12)` с индивидуальной случайной солью; одинаковые пароли дают разные хэши. Сравнение выполняет `PasswordEncoder.matches`. Для неизвестного пользователя тоже проверяется фиктивный bcrypt-хэш, чтобы уменьшить различие во времени ответа. Ошибка входа одинакова для неизвестного логина и неверного пароля.

JWT подписывается HS256 и действует 15 минут. Поля: `sub` — ID, `iss` — `itmo-secure-api`, `aud` — `itmo-users`, `iat` и `exp`. Spring Security Resource Server проверяет подпись, фиксированный алгоритм HS256, срок действия, издателя, аудиторию и наличие обязательных полей. Просроченные токены отвергаются без временного допуска. JWT — подписанные, а не зашифрованные данные; пароль в них отсутствует.

Доступ без аутентификации разрешён только для POST `/auth/register` и POST `/auth/login`. Остальные маршруты требуют JWT. Сервер не создаёт сессию; Basic auth, cookie auth и JWT в query-параметрах не используются. CSRF отключён именно для этой модели с явно передаваемым заголовком Authorization. При переходе на cookie-аутентификацию потребуется пересмотреть CSRF-защиту.

Для учебного локального запуска используется HTTP. При публикации нужны HTTPS, ограничение частоты регистрации/входа и управление секретами. Механизма досрочного отзыва отдельного JWT нет: он действует до `exp` либо до смены ключа.

Smoke-скрипт выполняет настоящие curl-запросы и добавляет профили с уникальными именами; не удаляет существующие данные. JWT скрывается в выводе.

Проверены 17 тестов: регистрация/вход/список; соль и bcrypt; отсутствие токена; неверные учётные данные; дубликат; валидация; лимит UTF-8 для bcrypt; некорректный JSON; обход входа SQL-инъекцией; хранение SQL как текста; XSS в двух ответах; повреждённая подпись и `alg=none`; истечение срока; неверные `iss`/`aud`; отсутствие `exp`; пагинация; запрет Basic и JWT в URL.

## SAST и CI

`.github/workflows/ci.yml` запускается при каждом push, pull request и вручную. Задание `tests-and-sast` поднимает PostgreSQL, запускает тесты, сборку и SpotBugs 4.9.8.5 с FindSecBugs 1.14.0. Ошибки анализа приводят к падению задания. Отчёты сохраняются даже при сбое.

В `spotbugs-exclude.xml` есть три узких исключения с объяснениями:

- `SPRING_ENDPOINT` только для `ApiController`: информационное обнаружение трёх HTTP-методов.
- `SPRING_CSRF_PROTECTION_DISABLED` только для `SecurityConfig`: API принимает JWT из заголовка и не использует cookie/Basic.
- `EI_EXPOSE_REP2` только для конструктора `Users`: внедрение управляемого Spring экземпляра `JdbcTemplate`, который не возвращается наружу.

Первоначальный запуск с пятью отметками сохранён в `docs/evidence/sast-initial.log`. После классификации и точечных исключений анализ успешен. Заявление «0» относится к результату с этим фильтром, а не к отсутствию первоначальных отметок.

## Контрольные вопросы

1. **Почему bcrypt вместо SHA-256?** SHA-256 специально вычисляется быстро, поэтому облегчает перебор паролей. bcrypt имеет настраиваемую вычислительную стоимость и соль для каждого пароля. Соль не позволяет переиспользовать заранее рассчитанные таблицы, стоимость замедляет каждую попытку перебора. Для bcrypt учтён предел 72 байта.
2. **SAST и DAST.** SAST анализирует исходники/байткод без запущенного сервиса и находит опасные конструкции. DAST отправляет запросы работающему сервису и оценивает наблюдаемое поведение. Наш SpotBugs — SAST; curl — функциональные и негативные проверки работающего API, не полноценный DAST-сканер. SCA отдельно проверяет компоненты и известные уязвимости зависимостей.
3. **Как работает JWT?** Токен состоит из Base64URL-заголовка, payload и подписи. Сервер формирует claims, подписывает заголовок и payload секретом. При каждом запросе проверяются подпись, алгоритм и ограничения claims. Клиент не может изменить `sub` или `exp` без нарушения подписи. Payload не зашифрован.
4. **Зачем аудит зависимостей?** Уязвимость сторонней библиотеки может дать обход аутентификации, утечку, отказ в обслуживании или исполнение кода даже при корректном собственном коде. Нужно регулярно сканировать прямые и транзитивные зависимости, обновлять их и разбирать применимость находок. Успешный скан отражает состояние известных данных на момент проверки и не доказывает полное отсутствие уязвимостей.
